# 指纹卡与 App 的安全方案

本文描述 Touch SD 指纹卡和 macOS App 之间，从配对、录入到解锁验证的流程和安全设计，供想自己开发 App 的人参考。卡和电脑之间的文件和包格式见 [CARD_PROTOCOL.md](CARD_PROTOCOL.md)，消息的确切格式以 `Sources/FingerCore/SecureCard.swift` 为准。卡的固件闭源，本文只写 App 能依赖的行为，不写固件内部的实现。

正文里的流程图保留了设计时的算法名，实际使用的算法以这张表为准：

| 项目 | 流程图里写的 | 实际使用 |
|---|---|---|
| 消息和图像加密 | AES-256-GCM | ChaCha20-Poly1305 |
| 卡身份签名 | Ed25519 | ECDSA P-256（PAM 模块用 Security 框架验证） |
| 密钥派生 | HKDF/HMAC-SHA256 | HKDF/HMAC-SHA512 |

---

## 1. 总体架构和基本原则

```
┌──────────── 指纹卡（闭源固件）────────────┐        ┌────────── Mac App（开源）──────────┐
│ 传感器 → 采图 → 加密、认证 ───────────────┼─ SD ─▶│ 验证、解密（只在内存里）            │
│ 保存：配对密钥、卡内解锁密钥               │  卷上  │ 质量判断 → 比对 → 录入/解锁流程      │
│                                           │  文件  │ 保存：模板（加密）、配对密钥（钥匙串）│
└───────────────────────────────────────────┘        └────────────────────────────────────┘
```

- **卡只负责采图和加密，比对在 App 里做。** 指纹模板只存在 Mac 上，卡上没有任何指纹数据。
- **安全性只依赖密钥，不依赖代码保密。** 协议、算法、App 代码都可以公开。每张卡、每台 Mac 的密钥在配对时随机生成，代码里不写死任何密钥。
- **只用标准密码算法和成熟实现**：X25519、ECDSA P-256、HKDF、ChaCha20-Poly1305、HMAC。Mac 上用 CryptoKit。
- **SD 卷上永远没有明文指纹图像。**

## 2. 密钥一览

| 名称 | 长度 | 在哪生成 | 存在哪里 | 用途 | 生命周期 |
|---|---|---|---|---|---|
| 卡身份密钥 `ID_card` | P-256 | 卡上随机生成 | 卡内，私钥不出卡 | 证明“是这张卡”；App 配对时记住它的公钥 | 到恢复出厂为止 |
| 配对密钥 `K_pair` | 256 位 | 配对时双方协商（X25519） | 卡内；Mac 的钥匙串 | 派生每次会话的密钥 | 到解除配对为止 |
| 卡内解锁密钥 `K_unlock` | 256 位 | 配对时卡随机生成 | **只在卡上**，从不发出 | 计算解锁因子（第 7 节），保证“卡必须在场” | 到解除配对为止 |
| 会话密钥 `K_c2h`、`K_h2c` | 各 256 位 | 每次会话由 `K_pair` 和双方随机数派生 | 双方内存 | 加密这次会话的所有消息 | 一次会话（最长 60 s 空闲） |
| 模板密钥 `K_tmpl` | 256 位 | App 首次运行时生成 | Mac 钥匙串 | 加密存盘的指纹模板 | 长期，可以轮换 |

Mac 钥匙串里的条目都设为“仅本机、设备解锁时可用”（`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`）。

## 3. 卡的固件（闭源）

App 可以依赖这几点：

- 卡只运行厂家签名的固件。
- `ID_card` 在卡上生成，私钥不出卡；恢复出厂时重新生成。
- 量产固件**没有任何明文读图、改寄存器的接口**。

## 4. 通信层：SD 卷上的文件和消息格式

卡把自己模拟成一个小 FAT 卷，App 通过原地读写卷上的固定文件和卡通信，读写都要绕过系统缓存（`F_NOCACHE`）。文件、包头和读写规则见 [CARD_PROTOCOL.md](CARD_PROTOCOL.md)。

### 4.1 消息格式

会话建立以后，所有消息都装在 [CARD_PROTOCOL.md](CARD_PROTOCOL.md) 的请求 / 应答包里加密传送：

```
包头：类型 0x30（应答 0xB0），标志 bit0 = 1（已加密）
附加认证数据 AAD = 包头前 8 字节："SDTM" | 版本 1 | 类型 | 标志
载荷 = 计数器（4 字节，小端）‖ ChaCha20-Poly1305 密文 ‖ 16 字节认证标签
  明文 = 会话内消息类型（1 字节）‖ 数据；应答明文以 0xFF 开头表示出错，后面是原因
  App → 卡 用 K_h2c，卡 → App 用 K_c2h
  nonce = 会话 ID（8 字节）‖ 计数器（4 字节，小端）
```

- 计数器每个方向各自从 0 开始严格递增，收到不大于上一条的计数器就丢弃，以此防重放。
- 每次会话的密钥都不同，所以同一个 nonce 不会在同一个密钥下重复使用。
- 认证标签验证不过的消息直接丢弃，不做任何处理。

### 4.2 会话建立（每次录入或解锁前）

```
App                                                        卡
生成随机数 N_app（16 字节）
OPEN { host_id, N_app }，用 HMAC(K_cmd, …) 认证  ──────▶
                                                           按 host_id 找到 K_pair，验证 HMAC
                                                           生成随机数 N_card（16 字节）
                                            ◀──────────── OPEN_OK { N_card }，用 HMAC 认证
双方各自计算：
  K_c2h ‖ K_h2c ‖ 会话 ID = HKDF-SHA256(K_pair, salt = N_app ‖ N_card, info = "fpcard session v1")
之后所有消息都按 4.1 加密
```

`K_cmd = HKDF(K_pair, info = "fpcard cmd v1")`。会话空闲 60 秒后作废，需要重新建立。开会话时双方还各生成一次性 X25519 密钥（见 7.4 的前向保密）。

## 5. 配对（每台 Mac 和每张卡之间只做一次）

前提：App 先要求输入 macOS 登录密码（LocalAuthentication 的“设备所有者认证”），防止有人趁你离开时把自己的卡配对到你的 Mac 上。

```
App                                                        卡
生成临时 X25519 密钥对 (b, B)、host_id（16 字节随机）
PAIR_INIT { 协议版本, host_id, B }  ──────────────────────▶
                                                           生成临时 X25519 密钥对 (a, A)
                                                           transcript = SHA256(版本 ‖ host_id ‖ B ‖ 卡序列号 ‖ A ‖ ID_card 公钥)
                                                           sig = Sign(ID_card, transcript)
                                            ◀──────────── PAIR_RESP { A, ID_card 公钥, sig }
验证 sig
双方：
  共享秘密 Z = X25519(自己的私钥, 对方的公钥)
  K_pair ‖ K_sas = HKDF-SHA256(Z, salt = transcript, info = "fpcard pair v1")
  校验码 SAS = 由 K_sas 映射成 4 步 × 2 颗灯的颜色序列（6 种颜色，约 2^20.7 种组合）
卡：两颗 RGB 灯循环显示 SAS
App：屏幕上显示同样的颜色序列，提示“颜色一致的话，请按一下指纹传感器”
                                                           用户按传感器 → 卡确认
用户在 App 里也点“一致”
                                                           生成 K_unlock，和 (host_id, K_pair) 一起保存在卡内
App：把 (host_id, K_pair, ID_card 公钥) 存进钥匙串
```

- 旁观者能看到 A、B，但算不出 Z，所以得不到 `K_pair`（X25519 的安全性）。
- 如果有中间人分别和两边配对，两边算出的 SAS 不一样，颜色对不上，用户不会确认。中间人一次猜中的概率约为 170 万分之一。
- App 记住 `ID_card` 公钥（首次信任后固定），以后每次会话可以要求卡用 `ID_card` 签名，防止卡被换掉。
- 卡最多保存 4 个配对，支持一张卡配对多台 Mac。

## 6. 指纹录入

前提：已配对，并且 App 先要求输入 macOS 登录密码。删除指纹、修改设置也一样。

```
App                                                        卡
建立会话（4.2）
ENROLL_BEGIN  ────────────────────────────────────────────▶
                                                           检测手指按下
                                            ◀──────────── FINGER_DOWN
                                            ◀──────────── FRAME × 2～3（每帧单独加密，带帧序号）
                                                           检测手指抬起
                                            ◀──────────── FINGER_UP
验证、解密（只在内存）
质量判断（部分按压 / 不清晰 / 太快 → 提示，不计数）
重复检测（和已录入的几乎重合 → 提示挪动，不计数）
合格 → 提特征，加入录入样本，更新进度和拼接图
……重复，直到 32 次合格按压……
ENROLL_END  ──────────────────────────────────────────────▶
生成模板：只保留特征和比对所需的小块归一化图，不存原始帧
用 K_tmpl 加密后存盘
清零内存里的所有图像
```

- 模板文件放在 App 的 Application Support 目录里，加密存放，离开这台 Mac 就解不开（`K_tmpl` 在钥匙串里）。
- 模板包含一些很小的归一化图像块，比对时做像素相关复核要用，所以模板本身仍然属于敏感数据，只能加密存放，不能上传。

## 7. 解锁验证

### 7.1 流程

```
App                                                        卡
建立会话（4.2）
VERIFY_BEGIN  ────────────────────────────────────────────▶
                                            ◀──────────── FINGER_DOWN、FRAME × 2～3、FINGER_UP
验证、解密、质量判断
每个合格帧和所有模板比对，任意一帧通过就算通过
├─ 不通过：失败计数 +1，按 7.3 处理，结束
└─ 通过：
   GET_SECRET { salt }  ──────────────────────────────────▶
                                                           检查：本会话里刚刚有过一次真实按压（2 秒内）
                                                           检查：频率限制（每分钟最多 5 次）
                                                           r = HMAC-SHA256(K_unlock, salt)
                                            ◀──────────── SECRET { r }（加密）
   用 r 和 K_tmpl 派生的密钥解开受保护的秘密（第 7.2 节）
   自适应更新：这次按压不重复的话，加进模板（每个指纹最多 80 张），重新加密存盘
清零内存里的图像和 r
```

### 7.2 用指纹保护 App 里的秘密

App 真正要保护的东西（比如保险箱的主密钥 `VK`）不能只靠一句“比对通过”来放行，而是用三样东西一起加密：

```
保护密钥 = HKDF( r ‖ K_tmpl派生值 , info = "fpcard vault v1" )
存盘内容 = AEAD(保护密钥, VK)
```

所以要解开 `VK`，需要同时满足：

| 条件 | 由谁保证 |
|---|---|
| 这台 Mac，已登录且钥匙串已解锁 | macOS（`K_tmpl`、`K_pair` 在钥匙串里） |
| 配对过的卡插在这台 Mac 上 | 密码学（`r` 只有卡能算，`K_unlock` 从不出卡） |
| 有人真的按了传感器 | 卡（没有真实按压就不返回 `r`） |
| 按的是录入过的手指 | App 的比对逻辑 |

这和 FIDO2 安全钥匙的 hmac-secret 扩展原理一样。

### 7.3 失败锁定

- 连续失败 5 次：锁定 30 秒。
- 累计失败 20 次：必须输入 macOS 登录密码才能继续用指纹。
- 失败计数加密存在钥匙串里，重启 App 不会清零。
- 卡上另外有一层独立的频率限制（`GET_SECRET` 每分钟最多 5 次），就算 App 被篡改也绕不过去。
- 只显示“通过 / 不通过 / 请重试”和质量提示，**不显示比对分数**，防止有人利用分数一步步逼近（爬山攻击）。

### 7.4 SSH 密钥、两步验证码和确认

- **SSH**：卡从 `K_unlock` 用 HKDF 派生一把 P-256 私钥（标签 `fpcard ssh v1`），私钥不离开卡。它和 `ID_card` 分开，因为这把密钥要签主机给的任意摘要，`ID_card` 如果也这样做就能伪造按压证明。每次签名消耗一次按压，和 SECRET、SIGN 共用每分钟 5 次的限额。App 的 Agent 只接受同一用户的连接，提示里显示发起请求的进程名。公钥不需要按压就能读。派生自配对，所以解除配对、恢复出厂后这把密钥就没了。
- **两步验证码**：密钥和其他条目一样存在保险箱里，只在 Mac 上计算。保险箱锁着时，绑定了验证码动作的那次按压同时用来打开保险箱。
- **指示灯**：已配对的 App 可以在加密会话里设置两颗灯的颜色（`SEC_IN_LED`），每秒续一次，3 秒没续或会话结束就交还卡，其他程序碰不到。亮度上限由卡决定。配对颜色和恢复出厂提示期间灯只归卡，请求先存着，结束后才生效，所以 App 不能伪造校验颜色。App 控制期间没有按压的蓝绿反馈。
- **指纹摄像头**：App 打开窗口（要 Mac 密码）后每秒向卡续一次，卡在有手指时把全帧用会话密钥加密发出，3 秒没续就停。帧的按压编号是 0，不能当按压证明用。图像只在内存里显示，不保存，SD 卷上和其他时候一样没有明文。窗口开着时按压照常识别（抬手后判定不是滑动才比对），录入、sudo、SSH、保险箱这些等按压的请求优先，这期间不刷新画面。
- **输入登录密码和自动键入文字的动作**：内容存在系统钥匙串，保护级别和配对密钥相同，配置里只有“已设置”的标记。登录密码只在屏幕锁定时输入，自动键入文字只在没锁屏时输入并打进当前窗口，两者互斥，同一次按压不会把文字打进密码框。系统只能告诉 App 会话是否锁定，不能告诉它密码框是否在屏幕上。打字前和打字途中每个字符、回车之前都重新判断，屏幕中途解开（比如 Touch ID）时密码剩下的部分不再输入。
- **前向保密**：开会话时双方各生成一次性 X25519 密钥，会话密钥由 `K_pair` 和共享秘密一起派生。`K_pair` 日后泄露，也解不开之前录下的通信。
- **`fingerconfirm`**：防手滑，不防入侵。比对在 App 里做，结果没有经过卡签名，能以用户身份运行程序的人也能绕过调用它的脚本。需要真正防攻击者的操作请用 sudo（模块用 root 拥有的公钥验证卡的签名）。

## 8. 解除配对、换设备和丢失

| 情况 | 处理 |
|---|---|
| 在 App 里解除配对 | 需要 macOS 密码；发送加密的 `UNPAIR`，卡删除对应配对（`K_unlock` 随之销毁，用它保护的秘密作废）；App 删除钥匙串条目。模板可以保留，可以用来配对新卡 |
| 卡丢了 | 在 Mac 上解除配对，删掉 `K_pair`。卡上没有指纹数据；拿到卡的人没有 `K_pair` 和模板，用不了 |
| Mac 丢了 | 用任意一台 Mac 的 App 恢复出厂。Mac 上的模板受钥匙串和登录密码保护 |
| 卡转手 | 卡上没有指纹，密钥也不绑定用户，所以转手不需要厂家介入。原主恢复出厂后交给新主人；新主人装 App、配对、录自己的指纹。不恢复出厂也能配对（4 个配对没满时），但原主的配对还留在卡上 |
| 怎么恢复出厂 | App 的“设备”页发起（要 Mac 密码），卡琥珀色慢闪等 30 秒，用户把手指放上去按住 5 秒，快闪后变红。发起命令不需要配对也不加密：新主人手上没有原主的 Mac 也要能做。**人在现场靠的是按压**：恶意软件能发起，但没有人按住就什么都不会发生；发起时已经放着的手指不算 |
| 指纹库和卡的关系 | `fingers.sealed` 的密钥只以包裹形式存在 `fingers.keys`，打开要卡用 `K_unlock` 算出的秘密加这台 Mac 钥匙串里的本机密钥。卡断开就从内存释放（Swift 不保证内存被抹除，这是降低风险）。锁屏不释放，否则锁屏时无法比对。解除配对或恢复出厂后 `K_unlock` 销毁：App 没退出时自动转给下一次配对，否则要重新录入 |
| 恢复出厂做什么 | 生成新的 `ID_card`，清空全部配对，旧 `K_pair`、`K_unlock` 不留副本。原主 Mac 上的配对随之失效，下次连接时自动删除 |
| 用 `VK` 保护的数据 | 解除配对前，App 先提示用户把 `VK` 改成由新卡保护，或者导出恢复密钥。否则数据会解不开 |

## 9. 固件升级

- App 把厂家发布的 `UPDATE.BIN` 写到卷上，卡自己校验并安装，新固件起不来时自动回到旧版本。格式和签名由厂家管理，App 只负责原样写入（`Sources/FingerCore/Updater.swift`）。
- 配对和 `ID_card` 在升级时保留。

## 10. 威胁模型

### 能防住

| 攻击 | 靠什么防 |
|---|---|
| 其他程序或用户读 SD 卷、偷指纹图像 | 卷上只有密文 |
| 重放录下来的数据 | 每次会话的随机数和计数器 |
| 篡改卷上的消息 | 认证标签 |
| 假卡或兼容卡冒充 | 没有 `K_pair` 就算不出合法响应；`ID_card` 签名可以发现卡被换掉 |
| 配对时被中间人攻击 | X25519 加上灯光颜色核对 |
| 偷走卡 | 卡上没有指纹数据，配对密钥不对外读出 |
| 偷走 Mac（没带卡） | 解不开 `VK`，因为缺 `r`；模板受钥匙串保护 |
| 读了开源代码再来攻击 | 代码里没有任何密钥 |
| 拿分数做爬山攻击、暴力试指纹 | 不显示分数；App 和卡上各有一层频率限制 |

### 防不住

- **Mac 已经被完全控制**：有 root 权限、能在钥匙串解锁时运行代码的恶意软件，可以读走密钥或 App 的内存。这对所有本机软件都一样。
- **同时拿到你的卡、已登录的 Mac，还能运行修改过的代码**：比对是在 App 里做的，这种情况下可以跳过比对，因为第 7.2 节表里前三个条件都满足了。以后改成在卡上比对才能补上。
- **假手指**：没有活体检测，硅胶或明胶指模有可能骗过传感器。
- **对芯片的物理攻击**：开盖、故障注入。这是消费级产品的防护，算不上银行级安全。
- 拒绝服务：比如拔卡、写坏卷上的文件。
